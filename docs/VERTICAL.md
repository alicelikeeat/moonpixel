# 垂直世界：自主建筑与无固定高度上限的塔楼

代码：`ios/Sources/MoonPixelCore/Vertical.swift`（坐标、平面图、塔楼与索引）、`TowerLife.swift`（承重、运输、入住、分层饥饿）、`TowerPlanner.swift`（需求、蓝图、硬约束、评分、施工）。界面：`ios/App/TowerPanel.swift`。测试：`TowerTests`。

## 1. 坐标与空间契约

- 逻辑坐标 `Cell3(x, y, z)`，三轴都是 `Int64`；x、y 与开放世界的格子相同，z 向上。
- **旧世界的映射**：现有开放世界就是地表参考层 z = 0；地下层是 z = −1（`Space.undergroundTop`），预留到 −16。这只是一份映射约定，旧存档的数据一个字节都没改，迁移不需要转换，也不会丢东西。
- **边界**：任一轴绝对值不超过 `Space.limit` = 2^40（约 1.1×10^12 格）。超出的运算返回 nil 并拒绝，绝不回绕（`Space.add` 用溢出检测的加法）。这是数值表示的范围，不是玩法上的高度上限。
- **区块**：32×32×16，`Space.chunk` 用向下取整的除法（−1 / 32 = −1）。
- **渲染**：`Space.render(cell, origin:)` 先用整数求差，再转成 Float，RealityKit 顺序为 (x, z, y)。离原点超过 2^23 时返回 nil，由调用方先移动原点。z = 2^39 处的格子相对附近原点能被精确绘制（有测试）。
- **存储**：楼层不保存自己的格子，只引用一张共享、不可变的平面图（`FloorPlan`），自己的改动另存为差异（写时复制）。空间里没有东西的地方不占存储。查询某一格时，先按二维区块索引找到附近的塔楼，再在楼层里二分查找。

## 2. 楼层、房间与可用空间

每张平面图都记录真实构件：楼板、墙、门、窗、柱、楼梯、电梯井，以及床、田、货架、机器、垛口、泊位。房间有用途、格子、入口和容量。只有满足以下检查的平面图才能使用（`Blueprint.check`）：
- 有楼梯；
- 每个房间的入口都能从楼梯走到；
- 每件设备旁边都有能站人的格子。

住户只会住在已经“使用中”的楼层；审计会拒绝任何住在未完工或受损楼层的人。

## 3. 承重（游戏规则，不是工程计算）

| 材料 | 每根柱承重 | 需要的科技 |
|---|---|---|
| 木构 | 40 | — |
| 石构 | 120 | 冶金 |
| 钢构 | 900 | 钢铁 |
| 复合材料 | 6000 | 机器人学 |
| 场升力 | 40000（需要供电，每层每天 0.6；断电时只按复合材料计算） | 场升力 |

- 每层的荷载 = 自重（构件数 + 柱 × 2）+ 住户 × 0.08 + 存粮 × 0.002，再加上它上方所有楼层的荷载。
- 承载能力 = 柱数 × 材料的柱承重 × (1 − 损伤)。
- 超过 100%：该层标为受损，它和上方所有楼层的人撤到地面。
- 超过 125%（或损伤满了）：该层及以上坍塌，只发生一次。仍在里面的人死亡，原因记为“坍塌”；坍塌写入塔楼的历史记录。
- 改动某一层只重算该层及以下各层，上方不动（`Tower.recomputed` 可以验证）。
- 没有“第 N 层禁止建设”的规则。高度受材料、柱数、成本、电力和运力限制：千层塔需要场升力，也就需要持续供电。

## 4. 把东西运上楼

- 楼梯每天 600 单位·层；每组电梯每天 9000 单位·层，电梯需要城市的富余电力，不足时按比例减速，完全没电时人工摇只剩六分之一。
- 运到第 k 层的代价是 k；设了空中转换层（每 N 层一个）之后，代价变成 (k / N) × 2 + (k mod N)。
- 运力不够时，每一层得到相同的比例，缺的那部分就是这一层真实的饥饿，规则和地面居民一样（有滞回、逐级恶化、会饿死）。地窖里的粮喂不到 300 楼。
- 水：每个水泵层把水往上送 40 层，没有水的楼层不住人。
- 垂直农场层用电力种出温室蔬菜，送进城市仓库。

## 5. 自主规划闭环

需求监测 → 选址 → 多个候选蓝图 → 硬约束校验 → 评分选择 → 预留材料 → 分段施工 → 入住 → 下一次查看时评估效果。

| 需求（`towerNeeds`） | 判断依据 | 动作 |
|---|---|---|
| 缺床位 | 人口 − 床位 ≥ 24 | 现有塔楼还有承重余量就加建，否则新建塔楼 |
| 高层缺粮而仓库有粮 | 有楼层送粮覆盖率 < 95%，且城市存粮够 8 天以上 | 加一组电梯；超过 60 层且没有转换层就设空中转换层（判定为运输问题，不当作粮食问题） |
| 粮食产量不足 | 存粮不足 10 天，且地面也吃不饱 | 加建垂直农场层（需要温室科技） |
| 高层缺水 | 有使用中的楼层没水 | 加建水泵层 |
| 战争 | 处于交战 | 在最高的塔楼顶加防御平台 |

每次决策都会写一句可读的理由，例如“缺 112 个床位，需要新建塔楼”，记入塔楼历史和新闻。每座城市至少隔 4 天才做一次决策，分数低于 20 的需求不处理。

- **蓝图**：语法生成，有三种布局：中心核、侧核、带中庭的院落。房间沿走道分隔，柱子落在墙的网格上，设备按用途放置。不同种子和布局会生成不同的方案（测试中至少 10 种住宅布局），不是同一张图换颜色。
- **地形**：河边加分院落布局，山地加分窄体型。
- **硬约束在评分之前**：平面图检查、施工中途的承重检查（逐层验收）、材料整段预留、受保护的塔楼和楼层不动。
- **施工**：自下而上逐层推进，每层经过 规划 → 备料 → 主体 → 装修 → 验收 → 使用中。下面一层到了装修阶段，上面一层才能开工；同时最多 3 层在施工。缺料就等，并在规划备注里写明原因。
- **材料**：选国家掌握、城市又买得起的最好材料。

## 6. 测试与数据（Linux 发布构建）

| 测试 | 结果 |
|---|---|
| 坐标 | 负数向下整除、越界拒绝、不回绕；z = 2^39 处相对原点精确绘制 |
| 蓝图 | 7 种用途 × 3 种布局 × 4 个种子 × 3 种尺寸全部通过检查；房间被墙隔断能检出 |
| 写时复制 | 改一层的一格，共用平面图的上层和平面图本身都不变 |
| 拥挤城市 | 自行规划塔楼并写明理由，消耗真实材料，居民住进已完工楼层，人口审计守恒 |
| 运力瓶颈 | 61 层、没有电梯：高层挨饿而仓库满仓；需求判为电梯或转换层，不是农场；加电梯和转换层后每层恢复到 ≥95% |
| 结构 | 拆掉第 4 层全部柱子：第 4 层及以上坍塌，死亡只记一次；改动顶层重算 30 层，改动第 5 层只重算 5 层 |
| 保护 | 受保护的塔楼不会被规划器加建 |
| 规模 | 10 / 100 / 1000 层（千层塔底座在 z = 2^38）：能按格子找到顶层，正常运转，存档往返一致；每游戏日 0.15 / 0.34 / 2.6 ms，各自只用 2–3 张共享平面图 |

## 7. 已知限制

- 塔楼目前只在区域层城市里运行。玩家附近详细世界的城镇不会自动盖楼；玩家自由建造的方块也还不是三维的。
- 没有塔楼的 3D 模型，也没有 2D 地图上的切片视图。目前只有面板里的逐层剖面：懒加载列表，可跳转，显示每层的状态。
- 一句话描述蓝图、可选的模型适配接口、玩家保存和复用蓝图库都没有做。
- 场升力断电时直接按复合材料计算承重，没有缓降过程。
- 居民在塔楼和地面之间整体迁移，没有个人通勤路径；电梯排队也只按每日运力估算，没有逐人模拟。
- 创世纪、归墟等世界法则尚未覆盖三维区域；存储写满时也还没有暂停扩建的保护。
- 真机未测。
